> **致 AI Coding Agent 的全局执行说明**：
> 本次 V2.3 升级将全面重构 `app_core/models/` 模型网关、打包器与 GUI【设置】界面，核心实现以下 5 大能力：
> 1. **三层解耦架构**：【统一模型算力池 (无限添加 API / 单位排队模型 / 网页版 AI / 本地 ONNX)】 $\rightarrow$ 【可编排模型调度策略 (自定义接力顺序、排队转交与循环等待)】 $\rightarrow$ 【五类业务角色支持按时间段绑定不同模型策略】。

> 4. **20 秒排队感知轮询与无缝接力**：每 20s 轮询状态（区分“排队中”与“已在处理中”），排队超时自动转交下一节点。

## Task 1：重构模型网关为“算力池（含独立包容量与时段）$\rightarrow$ 模型策略 $\rightarrow$ 分时段角色绑定”三层架构 (`app_core/models/`)

### 1.1 第一层：统一模型与算力池 (`EndpointPool` — 每个节点独立配置包容量与可用时段)
允许用户在算力池中创建无限个算力节点（`EndpointNode`），每个节点包含：
1. **基础标识与连接信息**：
   * `node_id` 与 `name`（如 `"单位内部-OCR大模型"`、`"Web-DeepSeek网页版"`、`"Web-Kimi网页版"`、`"主力API-deepseek-flash"`、`"本地-Ollama-BGE-M3"`）。
   * `node_type`：`OPENAI_COMPATIBLE_API` / `QUEUE_POLLING_API` / `WEB_AI_PLAYWRIGHT` / `SEMI_AUTO_CLIPBOARD` / `LOCAL_ONNX`。
   * `capabilities`：`["TEXT_LLM", "VISION_VLM", "EMBEDDING", "RERANK"]`。
2. **节点专属包容量配置 (`node_batch_capacity` —— 针对不同模型量体裁衣！)**：
   * `max_input_tokens`：该节点单次请求允许的最大输入 Token 数（例如：Web AI 节点默认设为 **`5,000`**；常规 API 节点可设为 **`32,000 ~ 100,000`**）。
   * `max_output_tokens`：该节点单次回复的最大安全输出 Token 数（例如：Web AI 默认 **`4,000`**；支持长输出的 API 可设为 **`8,000 ~ 16,000`**）。
   * `max_items_per_batch`：单包最多装载的证据片段数（例如：Web AI 默认 **`6`** 个片段/包；大容量 API 可设为 **`25 ~ 50`** 个片段/包）。
3. **节点可用/畅通时间窗 (`active_time_window` —— 避开白天拥堵或锁定半价时段)**：
   * `time_restriction_enabled` (布尔开关，默认 `False` 全天可用)。
   * `allowed_start_time` 与 `allowed_end_time`（如设为 `18:00` 至 `08:30`，支持跨午夜）：当开启时段限制且当前系统时间不在该区间内时，接力执行器在遍历策略链时**0 毫秒自动跳过该节点**（例如白天自动绕开拥堵的单位内部模型，夜间自动启用！）。
4. **节点排队与轮询参数**：
   * `poll_interval_sec`（默认 **`20` 秒**）、`max_queue_wait_sec`（默认 **`120` 秒**，排队超时则转交下一节点）。

### 1.2 第二层：可编排“模型调度策略” (`ModelStrategy` — 接力链与全链循环回退)
允许用户创建多套命名策略（如 `模型策略 1：白天Web白嫖链`、`模型策略 2：夜间单位模型+半价大包API链`）。每套 `ModelStrategy` 包含：
* `strategy_id` 与 `strategy_name`。
* `relay_chain`：由算力池中的多个 `node_id` 按先后优先级组成的有序列表（如：`[Web AI 1] -> [Web AI 2] -> [免费 API 1] -> [付费 API 2]`）。
* **全链冷却循环策略 (`loop_retry_policy`)**：
  * `enable_loop` (默认 `True`)：当链条中所有当前可用节点均因排队超时/限流未能完成时，等待 `loop_cooldown_sec`（如 `60` 秒）后，**自动回到链条第 1 个节点重新循环尝试**（最多循环 `max_loops` 轮，仍未完成则转入半自动待办队列，绝不丢失任务）。

### 1.3 第三层：五类业务角色支持“分时段动态切换模型策略” (`TimeAwareRoleBindings`)
对于 `快速提取模型`、`深度归纳模型`、`图像理解模型`、`向量模型`、`重排模型` 五大角色，每个角色支持绑定：
1. **`default_strategy_id`（默认模型策略）**：未命中特殊时段规则时使用的策略（如 `模型策略 1`）。
2. **`time_slot_rules`（分时段策略自动切换规则列表，可添加多条）**：
   * 每条规则包含：`rule_name`（如 `"夜间通畅与半价时段"`）、`start_time`（如 `"18:00"`）、`end_time`（如 `"08:00"`，支持跨午夜）、`target_strategy_id`（如 `"模型策略 2"`）。
   * **运行时动态路由**：每次发起任务时，调度器根据当前系统时间 `datetime.now().time()` 自动匹配生效的 `ModelStrategy`！例如白天自动走 `策略 1（小包 Web AI 链）`，一到晚上 18:00 下班或凌晨半价时段，无需人工干预，自动无缝切换为 `策略 2（单位高速模型 + 10万Token超大包半价 API 链）`！

## Task 2：实现纯算法、零模型的“自适应动态弹性分包器 (`DynamicBatchPacker`)” (`app_core/parser/batch_packer.py`)

彻底摒弃静态预打包模式，采用**“纯算法实时按节点容量动态装包 + 接力转交时自动重切分/重合并”**机制（全程纯算法计算，0 神经网络调用，耗时 `< 0.5ms`）：

1. **纯数学 Token 估算器 (`estimate_tokens_fast`)**：
   * 无需加载重型模型，使用纯算法公式快速计算任意文本片段的 Token 占用：
     `est_tokens = int(英文单词与数字串数量 * 1.3 + 中文字符数 * 0.7 + LaTeX公式与代码块符号数 * 1.4)`
   * 每个候选证据片段（`DistilledItem`）预先设定预估输出占用 `est_output_tokens = 550`（确保大模型有充足输出空间，不发生截断）。
2. **基于待处理双端队列 (`Deque[DistilledItem]`) 的临发前动态装包 (`checkout_batch_for_node`)**：
   * 一篇文献（或跨文献任务池）经过四通道探针筛选后，生成有序的待处理片段双端队列 `pending_queue` 及一张全局 `shared_refs_map`（存放可复用的 `Table I`、`Model A/B/C` 定义及文献全局前提）。
   * **当执行器选定当前接力节点 `node` 时**，根据该节点的 `node.max_input_tokens`、`node.max_output_tokens` 和 `node.max_items_per_batch`，利用贪心滑窗算法从 `pending_queue` 头部依次取出片段装入当前包：
     * 动态计算：`当前包输入总 Token = 固定系统指令 Token + 文献全局前提 Token + 当前已选片段引用的共享表格字典并集 Token + ∑(已选片段 Token)`；
     * 动态计算：`当前包预计输出总 Token = 已选片段数 × 550`；
     * 只要加入下一个片段不超出 `node.max_input_tokens`、不超出 `node.max_output_tokens` 且片段数 `< node.max_items_per_batch`，就继续装入！
     * *(注：若某单个超大表格片段自身就达 `8,000` Token，而当前节点上限为 `5,000` Token，算法支持自动按段落/表行边界将其平滑拆分为两个子片段装包，绝不卡死队列！)*
3. **跨容量节点转交时的“自动退回与弹性重塑（Auto Re-Slicing / Coalescing）”**：
   * **大包转小包（如 `100,000 Token` API 失败 $\rightarrow$ 转交 `5,000 Token` Web AI）**：
     若发往大容量 API 的 30 片段大包因限流或网络失败，这 30 个未完成片段立刻原样退回 `pending_queue` 头部；紧接着转交给 `5,000 Token` 的 Web AI 节点时，`checkout_batch_for_node` 自动每次只取 **5~6 个片段** 组装成 `5,000 Token` 的小包逐批发送！
   * **小包合并大包（如 `5,000 Token` Web AI 排队超时 $\rightarrow$ 转交 `100,000 Token` API）**：
     若第 1 个 6 片段小包在 Web AI 节点排队超时，这 6 个片段退回 `pending_queue` 头部；紧接着转交给 `100,000 Token` 的 API 节点时，`checkout_batch_for_node` 自动将这 6 个片段与队列后面剩余的 24 个片段**瞬间合并为一个 30 片段的超大包**，一次 API 请求直接清空整条队列！

## Task 3：实现“每 20 秒排队感知轮询 + 自动接力”执行器 (`app_core/models/relay_executor.py`)

1. **双模式 20 秒排队轮询**：
   * **异步状态轮询（针对单位内部 OCR/大模型队列）**：提交任务后每隔 **`20 秒`** 发送一次状态查询请求，并在【工作台】实时显示：*`⏳ 节点 [X] 正在排队中 (已等待 40s / 阈值 120s)...`*。
     * 若返回 **`已在处理中 (processing / running)`**：立即解除排队等待超时限制，继续每 20 秒轮询直至计算完成返回结果，**绝不在计算中途超时中断**！
     * 若返回 **`排队中 (queued / pending)`** 且累计排队时间超过 `max_queue_wait_sec`，或返回 `429 / 503`：主动取消当前节点请求，将当前包内片段退回 `pending_queue` 头部，立即转交策略链的下一节点（并根据下一节点的容量重新动态分包）！
   * **流式首字心跳监测（针对标准流式 API）**：在收到第 1 个输出 Token 前每 **20 秒** 检查一次；若首字等待超过 `max_queue_wait_sec` 则断开并转交下一节点；一旦收到首字则持续接收直至生成结束。
2. **部分成功容错**：若某个包含 20 个片段的大包返回了前 15 个片段的合法 JSON，仅将已成功的 15 个片段移出队列落库，剩余 5 个片段留在队列中继续处理，绝不浪费已生成的任何一张卡片。
